# JD 批量导入与智能解析

在“岗位与 JD”点击“批量上传并智能解析”，一次选择多份文件，每份对应一个岗位。原来的“手工添加”仍然可用。

编辑或手工添加岗位时，也可以在“JD 原文”下方点击“智能分析”。系统先显示覆盖提示框，点击“确认覆盖并分析”后才调用模型。分析成功会覆盖岗位名称和结构化要求（未识别的字段清空），取消已核对勾选，并展示逐项原文依据；失败或取消则保留原有内容。JD 原文、销售岗位标记、评分权重和自定义细则保持不变。分析仅回填表单，需要点击“保存 JD 版本”才会写入岗位。默认细则描述随新要求在保存时同步，自定义细则需核对。

## 岗位删除、停用与启用

“岗位与 JD”卡片显示关联申请和历史评分数量，并提供带确认框的操作：

- **删除**：仅限未关联任何候选人申请、也没有历史评分的岗位。服务器在事务中重新校验，不能通过过期页面绕过限制。确认后删除岗位及其所有 JD 版本，页面无法恢复；已上传的原始文件及导入日志保留，避免删除被其他岗位共用的原件。批量导入记录显示“关联岗位已删除”，不会自动重建岗位。
- **停用**：停止参与新简历的岗位匹配，不允许上传或手工分类到该岗位。无法匹配到启用岗位的新简历保留在待分类区，不丢弃附件。已有未评估申请暂停评估；历史 JD、已完成评分、报告和人工跟进字段保留，可继续查看。姓名与岗位由大模型结合附件名、邮件主题和简历文字识别，不按固定文件名格式拆分。
- **启用**：恢复新简历匹配。已有待分类记录仍需人工确认岗位；已有待评估记录可点击“处理已上传简历”继续，历史评分不会自动重算。

停用岗位仍可编辑 JD；保存新版本不会自动启用。正在运行简历任务时不能删除或改变岗位状态。确认期间 JD 被修改会要求刷新后重新确认。删除一个岗位不能用来删除其历史招聘记录。

## 使用步骤

1. 在“连接与设置”填写公司批准的模型接口、模型名称、API 密钥和批准说明，并启用批准开关。无需先配置邮箱或院校名单即可解析 JD。
2. 选择 PDF、DOCX 或 UTF-8 TXT；每批最多20份，每份不超过20MB。PDF 最多40页，扫描 PDF 会尝试中英文 OCR。
3. 点击“上传并智能解析”。文件逐份上传，服务器保存原件并在后台串行处理。**上传完成后**可离开页面；刷新或重新登录后仍能看到导入记录。
4. 点击每份文件的“核对 / 补充”。左侧展示原文，右侧自动填入岗位名称、学历、年限、地点、证书、到岗时间、职责和技能。各项均可展开原文依据，并可人工修订。地点与到岗时间仅作可选备注，不计分、不检查缺失。
5. 选择“新建岗位”或明确选择已有岗位创建新 JD 版本。选择已有岗位时请核对名称及销售属性；既有评分细则沿用，默认条目随新要求更新，自定义条目保留，保存后可在岗位编辑页调整。
6. 勾选逐项核对后保存。未勾选“批准本版 JD”时保存为草稿；五项评分条件（学历、年限、证书、职责、技能）及原文完整且经人工批准后，才允许用于简历评估。销售岗位豁免不会由模型自动确认。

## 缺失、重复和失败

- 原文未写明的条件留空。**缺失不等于不限**；请明确实际要求，只有确认不受限制时才填“不限”。未确认的 JD 不用于评估。
- 提取值由模型按原文含义整理，第二次调用模型复核“必须”“优先”“或”“例外”等限制。模型只返回来源编号和解读，服务器按编号附上真实原文；不要求解读与原文逐字一致。界面分开展示两者，仍需人工核对 OCR 结果和业务要求。
- 模型若识别出多个独立岗位，会要求拆分文件，不合并创建岗位。
- 同一内容再次上传会复用已有记录，即使文件已改名。已保存的记录可直接打开对应岗位；需要修改时编辑岗位并保存新版本。
- 单个文件失败不影响其他文件。模型失败时保留已提取文字，可手工填写或手动重试；文档无法解析时保留原件，需提供可解析版本。
- 服务器重启后，尚未开始的任务继续排队；正在解析或调用模型的任务标记为中断，需手动重试，避免自动重复调用产生费用。
- 每份新 JD 通常调用两次模型（分析、语义复核），两次均可能计费。第二步失败后保留分析草稿，输入和模型配置未变时，手动重试仅继续复核。队列最多同时等待50份，导入列表显示最近300条（未保存记录优先）。历史原件、结果及版本继续保存在服务器。
- JD 导入独立于简历任务；“单次最多模型调用数”仍限制简历评估任务，JD 导入按每批20份、队列50份控制。

## 数据与版本

复用既有登录、CSRF、文件权限及公司批准的模型连接。模型仅接收 JD 提取文本（常见邮箱、手机号码、身份证号先脱敏）；原始附件不发送到模型。两次调用使用同一接口与设置快照，复核输入还包含第一次结果。导入结果保存模型名称、规则版本、来源编号、模型解读、真实原文和两阶段用量摘要，日志不记录密钥或全文。分析草稿属于本地业务数据，随数据库保留，不属于每天清理的详细诊断日志。

模型不会直接创建已批准的岗位、修改全局学历规则、改变评分权重或自动覆盖同名岗位。保存时同时登记导入状态和 JD 版本；重复点击不会重复创建。已有岗位在核对期间被修改时会提示版本冲突，需要重新打开核对。

## 模型响应等待与失败排查

### 简历并行处理

在“连接与设置”填写“同时处理简历数”，范围1—10，默认1为串行，建议先试2。保存后从下一批收件、待处理简历或姓名岗位核对任务生效；运行中的批次采用启动时的并行数。不同候选人可同时处理，每份内部仍按分析、语义复核的顺序执行，JD任务继续使用原队列。

智谱支持并行请求，具体额度取决于账号、模型及平台实时限流，查看[官方速率限制说明](https://docs.bigmodel.cn/cn/api/rate-limit)和账号控制台。工作台允许填写的上限不是供应商授予的额度；其他应用或JD任务也可能消耗同一账号额度。并行可能缩短整批等待时间，不保证单次响应更快，也不会减少每份正常分析所需的调用次数。

所有并行候选人共用每批1—1000次调用预算，分析与复核分别计数。发生超时、限流或其他模型调用故障后停止新增调用，已发出的请求可能继续完成；等待这些请求结束并保留成功结果、可续用分析草稿后，再生成报告并结束批次。不会自动重试。`BATCH_STOPPED`表示该候选人受同批次暂停影响，后续请求没有发送，不是一次新的模型失败。下一批手动继续即可，已有成功评分与人工跟进不自动重写。

### 响应等待与错误说明

“连接与设置”可填写模型响应等待时间，范围30—600秒，默认300秒。此值控制等待响应数据的读取超时，建立连接、发送请求及等待连接池各最多30秒，并非整个任务的总时长。升级会一次性将旧版隐藏的90秒默认值改为300秒；已有其他自定义值保留，之后手动设置的值也不会在重启时被覆盖。

模型超时、连接失败、鉴权失败、接口拒绝和 JSON 格式错误会分别显示原因。JD 编辑器直接在智能分析按钮下方显示具体错误，并保留已填写内容；失败原因也写入运行日志。日志不包含密钥、模型原始响应或 JD/简历全文。程序接受纯 JSON 或一个完整 JSON 代码块，核验字段结构和来源编号，不尝试补全截断的 JSON，也不把思考过程作为结果。

## 姓名、岗位与简历评分的语义复核

姓名岗位识别、JD 解析和简历评分均采用“模型分析 → 第二次模型语义复核”。第二阶段重新阅读原始输入，检查并修正第一次结论，返回完整的最终业务结果。模型负责语义判断；程序负责结构、来源编号、已确认政策、分数计算、数据权限与版本保护。不会因为模型使用同义表达、整理数字单位或规范院校名称而要求其与原文逐字匹配。

模型引用必须关联本次输入中的来源编号。候选人详情和岗位报告把“模型解读”作为解释文字，把“对应原文”作为可展开的服务器原文；Excel 证据表也分别保存两列，长原文分行保存。模型不能自行生成被展示为原文的引句。

某评分条目没有来源依据时，统一为“未知”、暂计0分，整份评估标为“待定、暂计分，需人工核验”。没有证据不等于不满足要求。如果模型原本给了确定结论但未附来源，日志记录 `EVIDENCE_DOWNGRADED`，计入本批次异常；“评估1、异常1”可表示已形成暂计结果。全局项目成果与稳定性不能豁免；仅已确认 JD 的硬性条目可由模型按语义判断为明确不作要求，程序据此给满分。

学历政策采用模型复核后的结构化分类：学历、是否已取得、招生方式、是否对应用户名录中的院校条目。院校只能选已确认名录的 ID，不能自行增加名录，不拼接不同教育经历。本科招生方式未说明，且没有非全日制、成人教育、自考、函授等明确例外时，模型标记为“未说明”，程序按用户确认规则默认通过该子条件；不会将其改写成“已核实统招”事实。明确例外按实际信息判断，资料存在矛盾或无法确认说明属于哪段教育经历时仍待核验。语义判断经模型分析与复核，不靠程序匹配特定词语。院校名录和学历取得状态仍须符合要求；销售豁免和硕士放宽保持原确认规则，未覆盖学历、在读及 OCR 学历依据转人工核验。

候选人详情的“为何待定”逐条显示原因和下一步：例如院校名录未能确认、明确不符合本科培养方式条件、学历尚未取得、关键资料来自 OCR、某个评分项缺少依据、硬性条目仅部分满足，或匹配分处于60—69分区间。同一人存在多项原因时一并列出。Excel总览的主要风险和建议、岗位HTML报告同步展示这些解释，人工跟进列保持不变。旧评估只根据当时保存的结果补充解释，不改变原分数或等级；历史数据不足时说明无法还原具体原因。

程序仍检查完整 JSON Schema、评分条目是否齐全、引用的来源是否存在，以及岗位或院校 ID 是否属于提供的选项。错误来源编号显示 `EVIDENCE_SOURCE_INVALID`，无效院校选项显示 `EDUCATION_CATALOG_INVALID`。最终结果若对同一事实仍返回冲突的多个值，会要求核对，不自动选取。日志只包含固定字段和条目序号，不记录候选人的实际取值。

姓名岗位识别出现 `IDENTITY_SCHEMA` 时，新日志显示固定字段类别、格式问题类型、问题数量及依据序号，不记录模型取值或未知额外字段的原始名称。旧日志若缺少这些信息，不能仅凭错误码判断具体缺项。`DUPLICATE_APPLICATION` 表示同一原件已有目标岗位申请，需人工核对，程序不会自动合并独立的跟进记录。

导出 Excel 时，不支持的控制字符只在导出显示中转换为 `[U+XXXX]` 标记，并通过单元格批注说明；原始文件和保存的依据不变。原文证据在转换后分段，避免超过 Excel 限制而丢失内容。超长自动汇总会注明显示缩短，完整内容仍在工作台；人工单元格不经过此转换。已有评分可在“报表与反馈 → 生成并下载总览”单独导出，无须重新调用模型。

模型请求附带完整 JSON Schema，继续使用 `json_object` 接口参数。兼容处理只规范明确的格式差异（如可选空值、单条证据对象、明确判定枚举），不补造事实、来源编号或评分条目，不采用模型自报分数。兼容成功记录 `MODEL_FORMAT_NORMALIZED`；结构无效记录 `MODEL_SCHEMA`，显示安全的字段路径和错误类型。

详细诊断标明第一阶段分析或第二阶段语义复核，以及是否复用已完成分析。每次实际调用都计入简历批次的调用上限：新身份识别通常2次、新评分通常2次。第一阶段完成后立即保存草稿；复核失败或剩余预算不足时保留，下次继续复核。资料、规则、模型或生成参数变化后会重新分析。“重新分析姓名与岗位”会明确刷新分析，失败仍保留旧建议并标明待继续；不会悄悄使用旧建议覆盖记录。

简历模型调用失败时停止本批次后续模型调用，已下载、解析和归档的原件保留。修正设置后，在工作概览点击“处理已上传简历”，或在候选人库点击“解析与评估待处理项”即可继续，无需重发邮件或重新上传。失败不会自动循环重试；手动继续会产生实际调用的费用。姓名岗位不明确属于待人工核对，不等同模型接口故障，可到“姓名与岗位核对”确认或重新分析。

身份版本为 `identity-v2-semantic-review`，JD 提取版本为 `jd-extract-v4-semantic-review`，评分版本为 `v9-admission-default`，本科招生方式政策版本为 `admission-default-v1`。旧未应用身份建议需重新分析后确认；已应用身份和历史评分保留。升级不会重算成功或暂计评分，只有显式申请重新评估才生成新结果。原先仅因未注明招生方式而待定的记录，也需重评后才采用新政策；缺失信息不会被修改为统招事实。人工跟进、JD 批准和评分权重保持用户控制。两次模型复核仍可能误判，不能替代人工决定。

通过反向代理使用同步的 JD 原文智能分析时，还需注意代理的请求等待时间；代理提前结束请求不会延长或取消后台模型调用。收到502/504时先查看运行记录，不要连续重复点击。简历批次和批量 JD 导入在后台运行，不会因页面请求等待时间结束而停止。

本次更新无需新增 Python 依赖。数据库启动时自动增加导入记录表，保留既有岗位、简历、人工跟进和设置；更新容器前仍应停服务并备份挂载数据。

## 地点、到岗时间与评分档位

地点（包括 base 地）与到岗时间不参与评估。默认硬条件20分分配为学历5、经验年限12、证书3。升级会为需移除这些条目的当前岗位创建新 JD 版本，保留历史版本和既有评分；原来未批准的草稿不会被自动批准。移除条目的分值优先转给同维度的经验年限条目；自定义细则没有该条目时转给同维度首项，若该维度没有剩余条目则以对应维度的默认条目替代。原有评分需显式申请重新评估才会变化。

每个条目只有满足、部分满足、不满足三个得分档位：分别为满分、一半向下取整、0分。证据不足是独立状态，暂计0分并标记待核验。30分条目对应30/15/0，5分条目对应5/2/0；总分由所有条目相加，因此不限于三个数值。本次未更改档位算法。
