# 数据与接口设计

版本：v0.2，2026-10-23。本文是待实现的开发契约，不代表接口或后台已经运行。

## 1. 模块边界

```text
app/
  api/                   本机 API、会话、来源校验
  domain/
    recruitment/         岗位、申请、评估、人工跟进
    workflows/           批次、步骤、重试与游标
    evidence/            来源文档、片段与引用校验
    reports/             总览合并、岗位报告、导出批次
    feedback/            同步、标准化、回放与规则草案
  adapters/
    mail_imap/           QQ 邮箱只读 IMAP 适配
    pdf_ocr/             文本抽取与本机 OCR
    llm/                 公司批准的云端模型
    excel/               支持范围内的 xlsx 读写
    notification/        站内通知与 Windows 通知
  infrastructure/        SQLite、文件存储、凭据、审计
  worker/                手动与计划任务共用入口
ui/                      生产前端（后续开发）
prototype/               当前交付的静态交互原型
```

目录是建议架构。招聘域依赖通用任务、证据、文件和审计服务，未来 HR 模块复用这些服务，不直接操作招聘业务表。

平台入口与业务导航分开：全局首页通过模块登记信息（module_id、名称、说明、入口、可用状态）展示功能。当前只有 recruitment 可预览；待规划方向不挂业务路由。招聘内部页面保留深链接，模块切换不清空其当前会话状态。这个入口扩展不改变现有招聘接口和数据归属。

## 2. 核心数据实体

主键使用 UUID。业务表带创建 / 修改时间，版本记录不可变。SQLite 启用外键约束，单写事务，按需使用 WAL；备份使用数据库备份接口，不能只复制活跃的 `.db` 文件而忽略 WAL。

| 实体 | 关键字段 | 约束与用途 |
|---|---|---|
| mailbox | id、account、folder、credential_ref、committed_cutoff、uid_validity、last_seen_uid | 账号配置与成功窗口；凭据只有引用 |
| run | id、trigger、window_start、window_end、status、config_snapshot、started_at、completed_at、stats | 固定运行范围与配置快照 |
| job | id、run_id、type、subject_id、state、attempts、lease_owner、lease_until、fencing_token、last_error | 可恢复步骤；过期租约才可接管 |
| mail_event | id、mailbox_id、uid_validity、uid、raw_message_id、received_at、subject、state | `(mailbox_id, uid_validity, uid)` 唯一 |
| attachment_receipt | id、mail_event_id、sha256、original_filename、media_type、size、blob_id、state | `(mail_event_id, sha256)` 唯一；多来源关系保留 |
| file_blob | id、sha256、original_path、size、parse_version、parse_status | sha256 唯一，原件不可变 |
| role | id、name、safe_folder、aliases、is_sales、active_jd_version_id、status | 岗位名称与目录名映射可审计 |
| jd_version | id、role_id、document_id、content_hash、requirements_json、missing_fields、approved_at | 原文、结构化内容和批准记录对应 |
| document | id、type、source_blob_id、extractor_version、text_hash、status | 简历和 JD 的文字衍生物 |
| evidence_span | id、document_id、page、paragraph、start_offset、end_offset、text、bbox、ocr_quality | 原文区间；只保存在受限业务存储 |
| candidate | id、name、verified_identity_key、created_at | 人员实体；没有可靠标识时不自动跨原件合并 |
| application | id、candidate_id、resume_blob_id、role_id、classification_status、first_recommended_at | 已定岗时 `(resume_blob_id, role_id)` 唯一；待分类尚无 role_id |
| application_source | application_id、attachment_receipt_id | 同申请多个来源；一个原件可多岗位 |
| assessment | id、application_id、jd_version_id、policy_version_id、model_snapshot、schema_version、input_hash、status、score、grade、gate_status | 历史评估追加；缓存键含所有影响结果的版本 |
| assessment_item | assessment_id、rubric_item_id、verdict、points、max_points、resume_span_ids、jd_span_ids、reason | 每项评分有来源与规则 |
| manual_followup | application_id、workbook_id、revision、raw_cells_json、normalized_feedback_json、synced_at | 五字段的本机只读镜像；原值和标准化结果分开 |
| report_export | id、run_id、state、source_fingerprint、target_fingerprint、manifest_path、backup_path | PREPARED / COMMITTED / CONFLICT；处理跨文件和 DB 提交 |
| policy_version | id、role_id、parent_id、rules_json、weights、thresholds、status、approved_at、rollback_to | DRAFT / APPROVED / ACTIVE / RETIRED |
| feedback_observation | id、application_id、followup_revision、assessment_id、usable、reason、label | 缺反馈不是负例；保留人类原文出处 |
| audit_event | id、run_id、entity_id、actor、event_type、result、safe_metadata、created_at | 脱敏事件；敏感详情引用受限记录 |
| notification | id、run_id、type、severity、payload_summary、state、attempts | 与报告提交独立重试 |

资格或匹配结论、人工进展、技术处理状态分字段存储。禁止把“不推荐”“解析失败”“未通过面试”塞入同一状态字段。

## 3. 状态与恢复

### 3.1 附件 / 申请状态

```text
DISCOVERED → DOWNLOADED → VALIDATED → PARSED → CLASSIFIED → ARCHIVED
                               │          │        │
                               ↓          ↓        ↓
                          QUARANTINED  WAITING_ROLE WAITING_JD
                                                        │
                                JD 已确认、原件已归档 ────┘
                                         ↓
                               READY_FOR_ASSESSMENT
                                         ↓
                              ASSESSED / WAITING_REVIEW
                                         ↓
                                 EXPORT_PENDING → EXPORTED
```

图示是业务阶段；实际实现分开持久化 `parse_status / classification_status / assessment_status / export_status`，避免一项重试覆盖另一项已完成事实。暂存文件、原件、OCR 输出和模型结果分别有独立校验与提交记录。

### 3.2 作业幂等键

```text
parse_key  = sha256 + extractor_version + ocr_version
assess_key = application_id + resume_text_hash + jd_version_id
             + policy_version_id + model_id_and_revision + prompt_version
             + response_schema_version + redaction_version
export_key = run_id + report_template_version + committed_assessment_set_hash
```

同键已成功的步骤返回既有结果。显式重评创建新评估请求，不能修改旧记录；若只是修复模型输出，可保留各次尝试，选中最终有效一次。

### 3.3 批次伪代码

```python
acquire_lease_with_fencing_token("recruitment-main")
cutoff = now_in_utc()  # 固定一次，不在分页时移动
run = open_or_resume_run(previous_committed_cutoff, cutoff)
preflight_configuration_and_storage()
persist_discovered_mail_events(scan_inbox(run.window))
for receipt in pending_receipts(run):
    download_validate_and_register(receipt)
    parse_or_quarantine(receipt)
    classify_archive_or_create_pending_item(receipt)
    assess_if_jd_and_evidence_ready(receipt)
prepare_role_reports_and_overview(run)
commit_report_files_and_export_manifest(run)
with database_transaction():
    verify_same_lease_fencing_token()
    mark_export_committed(run)
    commit_mail_cutoff(run.window_end)
    finish_run(success_or_success_with_exceptions)
enqueue_local_notification(run)
release_lease()
```

这不是可执行代码；异常路径须遵守产品文档的“全局错误不推进游标”。报告提交与数据库不能原子地跨介质完成，因此用导出清单和状态恢复，而不是假设一个事务能同时覆盖 NTFS 和 SQLite。

### 3.4 崩溃恢复规则

- 下载完成但 DB 未登记：扫描受控临时区，按哈希与下载清单认领；不扫描用户其他目录。
- 模型返回后 DB 未提交：响应先写受限结果缓存并带请求 ID，再提交评估；若供应商支持幂等键则使用，不假定其一定支持。
- 文件已经替换但 DB 未确认：读取目标文件里的 export_id、内容哈希与清单，匹配才补记 COMMITTED，避免重复追加。
- DB 已提交但通知失败：仅重试通知。
- 任务租约过期被接管：旧执行者必须在任何提交前核验 fencing token，不能继续写表。

## 4. 模型输入和输出契约

### 4.1 输入

传入匿名申请 ID、已批准的 JD 条目、允许引用的简历 / JD 片段、分项判定定义。简历正文标为不可信数据，不包含邮箱授权码、任意工具权限、文件系统写入接口或可执行命令。

截断必须显式：长简历按页 / 章节分段提取并聚合，不能只取开头就宣称评估完整。预算不足则待处理，不输出低质量完整评分。

### 4.2 输出示例

以下是虚构示例的结构，仅用于说明契约；所有字段均须通过本机 schema 和引用校验。

```json
{
  "schema_version": "1.0",
  "application_id": "demo-application-a",
  "jd_version_id": "demo-jd-backend-v1",
  "facts": [
    {
      "key": "employment.backend_months",
      "value": 60,
      "unit": "month",
      "source_span_ids": ["R-A-01"],
      "certainty": "explicit"
    }
  ],
  "judgments": [
    {
      "rubric_item_id": "skill.database",
      "verdict": "met",
      "resume_evidence": [{"span_id": "R-A-02", "quote": "负责索引调整与慢查询治理"}],
      "jd_evidence": [{"span_id": "J-A-03", "quote": "具备数据库性能优化经验"}],
      "reason": "简历描述了与要求一致的实际职责",
      "unknowns": [],
      "interview_question": "请说明定位慢查询的方法、指标及本人承担的工作"
    }
  ]
}
```

模型不输出最终录用判断，不具有自主选择工具的权限。若需草拟优势 / 风险，每条文字也必须带引用列表，未知内容不能补齐。

### 4.3 本机验证

1. JSON schema、枚举、长度、允许的 rubric ID 和申请 / JD 版本匹配。
2. quote 必须在对应 span 中精确存在，span 必须属于当前申请或 JD；页码由程序从索引补入，不信任模型自报。
3. 条目引用能支持结论，数值 / 日期事实必须对应证据；引文存在只能证明出处，不能证明结论一定正确，抽样人工复核仍不可省。
4. 关键事实冲突、OCR 质量差、模型判定无证据时转 unknown，不能视为 met。
5. 本机确定性规则复核学历名录、日期区间、硬条件、分数上限和等级边界。
6. 不合格输出最多一次受限纠正；服务超时可按独立网络重试策略处理。所有尝试保留脱敏审计与用量，避免无限循环。

## 5. 确定性评分契约

```text
每条 rubric:
  dimension, max_points, awarded_points_by_verdict,
  critical, required_evidence, approved_source

dimension_score = Σ 本维度条目已验证判定对应的分值
total_score = Σ 五维分数
base_grade = [0,60) 不推荐；[60,70) 待定；[70,85) 推荐；[85,100] 强烈推荐

若 JD 不完整或解析 / 模型验证失败:
  score = null; grade = null; assessment_status = BLOCKED
否则若 critical fail / unknown 或有尚未复核的必要条目:
  grade = min(base_grade, 待定); score_kind = provisional（有未知时）
否则:
  grade = base_grade
```

各维度可采用小数细则，但等级按未四舍五入总分判断，显示精度保持一致；初版建议条目使用整数，避免 84.6 显示 85 却等级不同。对外总览字段统一以整数细则生成。

每次激活规则必须验证：五维上限 20/30/30/10/10、条目权重总和、等级阈值递增、硬条件封顶有效。自定义权重需要明确创建新政策版本，不能在正常运行时自行漂移。

## 6. Excel 更新协议

### 6.1 内容归属

机器字段允许由批准的评估结果更新。五个人工字段没有后台更新 API：应用仅通过 `import_followup_from_excel` 读取并形成镜像。即使反馈标准化为枚举，也必须保留原始文本。

隐藏 `_application_id` 跟随整行排序；机器和人工列不能分区分别排序。对用户改动机器字段，要显示差异并确认处理策略，不能把它作为可靠的原始简历事实。

### 6.2 安全合并

```text
检测工作簿类型、占用、表头和行 ID
    ↓
获取软件写锁 + 原始文件指纹 + 五字段快照
    ↓
合并机器字段（人写列原值保留）并稳定排序
    ↓
写同卷临时 xlsx + 导出 manifest + 原文件备份
    ↓
重新打开校验：ID 唯一、行数、五字段值 / 类型 / 公式 / 样式
    ↓
提交窗口再次核验源指纹；使用经 Windows 验证的排他写入 / 替换机制
    ↓
源已变化或锁冲突 → 标记 CONFLICT，保持原文件，后续从最新源重算合并
    ↓
安全替换后校验目标指纹，记录 COMMITTED
```

仅用软件侧 `.lock` 文件不能防住 Excel 修改；文件指纹检查本身也存在检查到写入之间的竞争窗口。实现时必须证明提交阶段的 Windows 文件共享 / 排他机制能阻止并发写，不能完成排他保护时就要求关闭 Excel 并延迟写入。该点必须以真实 Excel 验收。

用户在外部改写 / 重命名文件、粘贴复制行、删除隐藏 ID、删除行均产生专门待办。禁止仅按“姓名 + 岗位”猜测覆盖。首次迁移允许人工确认映射并记录审批；没有已确认映射不能自动写表。

### 6.3 测试比较口径

按申请 ID 对比五个人工字段的 `(value, data_type, formula, number_format, relevant_style)`，不能只比较最终显示文本。公式不求值；保留外部计算导致的缓存差异说明。机器文本防止 `= + - @` 开头被当作公式，数字匹配度和日期仍用明确的原生类型。

## 7. 本机 API 草案

所有修改需要有效本机会话；文件下载基于已登记 ID 解析路径，不接受客户端传入任意绝对路径。

| 方法与路径 | 用途 | 副作用边界 |
|---|---|---|
| GET /api/dashboard | 最新批次、待办、状态 | 只读 |
| POST /api/runs | 手动执行，带 idempotency_key | 本次批次，共用任务锁 |
| GET /api/runs/{id} | 进度、统计、阶段明细 | 只读 |
| POST /api/runs/{id}/cancel | 在安全边界取消 | 不删除已归档结果 |
| POST /api/work-items/{id}/retry | 定向重试失败阶段 | 复用前置成果 |
| GET /api/applications | 分页 / 筛选申请 | 只读 |
| GET /api/applications/{id} | 原件、证据、历史评估、五字段镜像 | 只读 |
| POST /api/applications/{id}/classify | 人工确认岗位 | 记录修改来源 |
| POST /api/applications/{id}/reassess | 显式重新评估 | 新版本，保留旧版与人工列 |
| GET /api/files/{id} | 授权读取原件或报告 | 仅受控登记路径 |
| POST /api/roles/{id}/jd-versions | 导入 JD 草稿 | 不立即生效 |
| POST /api/jd-versions/{id}/approve | 确认结构与缺失项已解决 | 激活当前 JD |
| POST /api/reports/sync-followup | 从 Excel 同步五字段 | 只改数据库镜像 |
| POST /api/reports/export | 合并机器结果到总览 | 受保护写入流程 |
| GET /api/reports/merge-preview | 合并差异与冲突 | 只读 |
| GET /api/feedback/analysis | 样本与失配原因 | 只读 |
| POST /api/policy-drafts | 生成有依据的规则草案 | 不激活 |
| POST /api/policy-versions/{id}/replay | 历史回放 | 不改正式推荐 |
| POST /api/policy-versions/{id}/activate | 明确批准后激活 | 版本化，可回滚 |
| POST /api/policy-versions/{id}/rollback | 回到已批准旧版 | 后续批次生效 |
| POST /api/settings/preflight | 测试连接 / 路径 / 模型就绪 | 不处理真实简历 |
| POST /api/settings/schedule | 启用 / 暂停计划 | 展示任务计划变更并由用户确认 |

错误返回含 `code / safe_message / retryable / affected_scope / run_id / action`，不把堆栈或秘密原样返回页面。

## 9. 生产验证与成本观测

- 单元层：文件名提取、路径限制、时间边界、去重缓存键、分数门槛、未知值与硬条件封顶。
- 集成层：中文 PDF / 扫描混合页 / JD 表格、邮箱增量、模型错误响应、原件哈希一致性、公式注入防护。
- 真正的 Excel 层：占用、读写冲突、日期 / 公式 / 样式、用户重排 / 删除、既有模板迁移。
- 故障层：逐阶段断电 / 杀进程、数据库锁、无磁盘空间、服务超时、报告提交后 DB 未提交。
- 业务层：用户对固定匿名样本逐条核对事实、证据、硬门槛和建议；不同规则版本回放结果明确。
- 费用按模型输入 / 输出 token 与 OCR 页数分开记账，设置单文档 / 单批次 / 每日预算。实际费用由供应商价格及实测用量计算，本设计不假定任何价格或速度。

静态原型不能作为上述任一生产集成通过的证据。
